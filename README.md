# Book Finder Assistant (Telegram)

Telegram-бот для поиска книг по **тексту** и **фото обложки**.

Главная идея: пользователь отправляет описание/цитату или картинку, бот определяет произведение и автора, затем ищет в **Флибусте** (приоритет), а если не уверен — делает fallback в **Google Books**.

## Какие задачи выполняет проект

### 1) Поиск книги по тексту
- Нажми `🔎 Find` в клавиатуре (или используй `/find <запрос>`), затем пришли обычный текст.
- Использует LLM (FreeLLMAPI с фолбэком на Gemini — см. [LLM provider](#llm-provider)) для извлечения структурированного запроса:
  - `query`
  - `title` (если уверенно)
  - `author` (если уверенно)
  - `title_ru` / `author_ru` (русское название и написание автора, если известны)
  - `confidence`
- Строит несколько попыток поиска и проверяет совпадения по скорингу.
- Приоритетно ищет во Флибусте; если не сработало — обращается к Google Books.

### 2) Поиск книги по фото
- Принимает фото в Telegram.
- Скачивает файл из Telegram и отправляет в vision-модель (FreeLLMAPI с фолбэком на Gemini).
- Извлекает вероятные `title/author/isbn/evidence`, а также RU/EN-варианты названия и автора (`title_ru`/`author_ru`/`title_en`/`author_en`/`variants`) для более надёжного сопоставления с русскоязычным каталогом. Через роутер второй шаг (RU/EN-варианты) — текстовый вызов без картинки.
- Каждое название ищется во Флибусте и отдельно без автора: vision-модели иногда уверенно выдумывают автора.
- Проверяет совпадение во Флибусте по всем этим вариантам (не только по исходной догадке) и формирует ответ со ссылками скачивания.
- Если уверенного совпадения нет — fallback в Google Books.

### 3) Интеграция с Флибустой
- Поиск книг и авторов через `flibusta-api`.
- Получение метаданных книги (жанры/описание).
- Генерация ссылок на форматы (MOBI/EPUB).
- Нормализация ошибок сети/таймаутов/403/429 в user-friendly сообщения.

### 4) Интеграция с Google Books (fallback)
- Поиск по сформированному запросу.
- Выдача лучшего совпадения и ссылки для открытия книги.
- Используется, когда Флибуста не дала уверенный результат.

### 5) Скоринг и матчинг результатов
- Нормализация текста (регистр, `ё`→`е`, пунктуация).
- Сравнение по exact/partial совпадению title и author.
- Дополнительный token-overlap скоринг для неполных запросов.
- Порог принятия для решения «совпадение/не совпадение».
- Логика вынесена в `src/core/matching.js` и покрыта тестами (`npm test`).

### 6) Кэширование
- Ограниченный (bounded LRU, до 500 записей) кэш ответов по SHA-256 хэшу изображения для фото — проверяется до любого LLM-вызова. У текстового поиска кэша перед LLM пока нет (TODO, см. P2-8 в `PRIORITIZED_FINDINGS.md`).
- Уменьшает повторные вычисления и ускоряет ответ на одинаковые запросы, не растёт бесконечно на долгоживущем процессе.

### 7) Режимы отладки
Включаются только через переменные окружения при старте процесса (это **не** Telegram-команды):
- `RAW_MODE=1` — показывает сырой JSON Vision-ответа (владельцу).
- `FLIBUSTA_DEBUG=1` — дебаг запросов к Флибусте (владельцу).
- `GEMINI_DEBUG=1` — шаги LLM для текстового и фото-поиска (владельцу): `via` (роутер или Gemini), модель, латентность, ретраи и фолбэки с причиной; для текста — ещё и сырой ответ модели.
- `LLM_DEBUG=1` — каждый LLM-вызов в лог процесса (stdout).

### 8) UX в Telegram
- Reply-keyboard меню после `/start`:
  - `🔎 Find` — начать текстовый поиск
  - `📩 Kindle email` / `✏️ Изменить Kindle email` — задать/сменить адрес доставки на Kindle
- Регистрирует команды бота через `setMyCommands`.
- Во время долгих операций (LLM/Флибуста) UI-отклик — это отладочные сообщения владельцу (см. п.7); обычный пользователь ждёт финальный ответ без промежуточного индикатора.

### 9) Kindle-доставка
- Если у пользователя сохранён Kindle email, под найденной книгой во Флибусте появляется кнопка `📩 Send to Kindle`.
- Файл (EPUB, иначе MOBI) скачивается и отправляется вложением на Kindle-адрес.
- Доставка через **Resend** (если задан `RESEND_API_KEY`) или fallback на **SMTP** через `nodemailer`.
- `/smtp_test` (только владелец) — проверяет, что доставка настроена и работает.
- Kindle email обязан заканчиваться на `@kindle.com` или `@free.kindle.com`.

### 10) Контроль доступа пользователей (onboarding)
Проект поддерживает модель доступа с owner-контролем:
- Новые пользователи отправляют запрос доступа кнопкой.
- Владелец получает заявку с кнопками Approve/Reject.
- Есть ручные команды владельца:
  - `/users` — список allowed/pending
  - `/allow <user_id>` (или reply на сообщение)
  - `/deny <user_id>` (или reply на сообщение)
- Есть дневной лимит запросов на пользователя (по умолчанию 15/сутки, владелец не ограничен) — см. `DAILY_LIMIT`.
- Состояние доступа, Kindle email и счётчики лимита хранятся в SQLite (см. «Хранилище данных» ниже).

### 11) Ограничение по топику/треду
- Можно ограничить обработку сообщений конкретным `ALLOWED_THREAD_ID` (0/не задано — без ограничения).

## Стек
- Node.js 20+ (ESM), встроенный `fetch` — отдельный HTTP-клиент не нужен
- Telegraf
- FreeLLMAPI — self-hosted OpenAI-совместимый роутер бесплатных моделей (пакет `openai`), с фолбэком на Gemini API; `zod` для проверки ответов
- flibusta-api
- Google Books API
- better-sqlite3 (хранилище: доступы, Kindle email, дневные лимиты)
- Resend / Nodemailer (доставка на Kindle)

> Обрати внимание: `flibusta-api` тянет зависимости, которым для сборки нужен Node **20+** (глобальный `File`); на Node 18 старт упадёт при импорте. Смотри, какую версию Node фактически использует твой деплой.

## Быстрый запуск
1. Установить зависимости:
```bash
npm install
```

2. Создать `.env` из шаблона и заполнить:
```bash
cp .env.example .env
```
Минимум: `BOT_TOKEN`, `OWNER_ID`, `GEMINI_API_KEY`, `GOOGLE_BOOKS_API_KEY`. Без `LLM_BASE_URL`/`LLM_API_KEY` бот работает только через Gemini, как до роутера. Все переменные с описаниями и значениями по умолчанию — в `.env.example`.

3. Запустить:
```bash
npm start
```

4. Прогнать тесты (матчинг, LLM-клиент, парсер JSON, схемы; без сети):
```bash
npm test
```

## LLM provider
Все LLM-вызовы идут через `src/llm/client.js`: сначала в [FreeLLMAPI](https://github.com/tashfeenahmed/freellmapi) (self-hosted OpenAI-совместимый роутер бесплатных моделей), а если он недоступен — напрямую в Gemini (`src/llm/gemini-direct.js`, тот же запрос, что бот слал до роутера). Для пользователя поведение не меняется.

| Шаг | Вызов | Модель роутера |
|---|---|---|
| Текстовый поиск (T1) | `chatJson` | `LLM_MODEL` |
| Чтение обложки (V1) | `visionJson`, `reasoning_effort: minimal` | `LLM_VISION_MODEL` |
| RU/EN-варианты (V2) | `chatJson` без картинки на роутере; Gemini получает картинку, как раньше | `LLM_LIGHT_MODEL` (по умолчанию = `LLM_MODEL`) |

**Когда уходим на Gemini** (в режиме `freellmapi_with_fallback`):
- сеть или таймаут (`LLM_TIMEOUT_MS` для текста, `LLM_VISION_TIMEOUT_MS` для картинок);
- ответы роутера 401/403/404 (ключ, хост или путь без `/v1`), 429 (пул исчерпан), 5xx; 400 на vision-запросе (модель без поддержки картинок);
- ответ, который не похож на API (например, HTML дашборда — в `LLM_BASE_URL` нет `/v1`);
- непригодный ответ после одного ретрая с «только JSON»: не JSON, не та форма (zod) или пустой по сути — у T1 нет ни названия, ни query, либо есть автор без названия; у V1 нет названия.

После 2 падений роутера подряд бот 60 с ходит сразу в Gemini. Невалидный `LLM_BASE_URL` выявляется при старте: бот работает только через Gemini и пишет предупреждение.

| `LLM_PROVIDER` | Поведение |
|---|---|
| `freellmapi_with_fallback` (по умолчанию) | роутер, при проблемах — Gemini |
| `freellmapi` | только роутер, без фолбэка; с битым конфигом бот не стартует |
| `direct` | только Gemini |

`LLM_LIGHT_MODEL` нужен, чтобы V2 не тратил дневную квоту Gemini: укажи профиль без моделей Gemini (Groq/OpenRouter). Такому профилю бот не шлёт `reasoning_effort`: `minimal` выключает thinking только у Gemini, а Groq это значение не принимает ни у одной модели.

Остальные переменные (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_LIGHT_MODEL`, `LLM_VISION_MODEL`, таймауты, `LLM_JSON_MODE`, `LLM_COVER_REASONING_EFFORT`, пороги `PHOTO_MIN_CONFIDENCE`/`TEXT_LOW_CONFIDENCE`) описаны в `.env.example`.

**Логи** (всегда): переход на Gemini с причиной, непригодный JSON вместе с моделью, которая его вернула, открытие предохранителя. Подробнее — `GEMINI_DEBUG` и `LLM_DEBUG` (см. п.7).

**Проверка вживую** (Node 20+, настройки из `.env`):
```bash
node scripts/llm-smoke.js [обложка]                       # chat, текстовый поиск, обложка: via/модель/латентность
LLM_BASE_URL=http://127.0.0.1:9/v1 node scripts/llm-smoke.js  # фейловер: всё должно уйти в Gemini
node scripts/llm-compare.js [--fallback]                  # роутер vs Gemini на 5 текстах и обложках из fixtures/ + Флибуста
```
Обложки для `llm-compare` кладутся в `fixtures/` (в git не попадают); ожидаемые названия — в `fixtures/expected.json` (`{"файл": ["название", ...]}`). По умолчанию роутер сравнивается без фолбэка, `--fallback` — как в проде.

Развёртывание FreeLLMAPI на Railway — чек-лист в [`docs/freellmapi-railway.md`](docs/freellmapi-railway.md).

## Статистика поисков
Каждый поиск, текстом или по фото, записывается одной строкой в таблицу `search_log` (SQLite). Пишутся и поиски владельца, и отказы по дневному лимиту. Текст запроса и фото **не хранятся**.

| Колонка | Что в ней |
|---|---|
| `ts` | начало поиска, ISO 8601 UTC |
| `kind` | `text` / `photo` |
| `cache_hit` | ответ из кэша по хэшу фото (у текста кэша пока нет, всегда 0) |
| `via` | `freellmapi` или `direct`; `direct`, если хотя бы один шаг ответил Gemini напрямую; пусто, если LLM не вызывался |
| `model` | модели шагов через `+` (у фото: обложка + enrich) |
| `latency_ms` | полное время LLM-части, с ретраями и ожиданием роутера перед фолбэком |
| `ok`, `error_kind` | `limit`, `no_details`, `low_confidence`, `not_found`, `llm`, `error` |
| `user_hash` | sha256 от `SEARCH_LOG_SALT` и Telegram id; пусто, пока соль не задана |
| `is_owner` | поиск владельца |

`ok` описывает первый ответ бота: показал варианты из Флибусты или Google Books (или ответ из кэша). Что пользователь выбрал потом, не пишется.

Отчёт (только чтение базы):
```bash
node scripts/usage.js            # последние 30 дней
node scripts/usage.js --days 7 --db path/to/bot.sqlite3
```
На Railway база лежит на volume бота, поэтому скрипт запускается там: `railway ssh -s <сервис бота> node scripts/usage.js`.

## Хранилище данных
Доступы, Kindle email, дневные лимиты и статистика поисков хранятся в SQLite (`better-sqlite3`, WAL-режим) в файле `bot.sqlite3` внутри `DATA_DIR`.

Если бот раньше работал на JSON-файлах (`access.json`/`kindle.json`/`limits.json`), при первом старте на новом коде эти файлы **автоматически** импортируются в SQLite (без ручных действий), а сами файлы переименовываются в `*.json.bak` (не удаляются — на случай отката). Дальнейшие старты миграцию не повторяют.

## Persistent storage (Railway Volume)
Если деплои сбрасывают данные (доступы/Kindle email/лимиты), подключи Volume и задай:
```
DATA_DIR=/data
```
Тогда файл `bot.sqlite3` будет сохраняться между деплоями.

## Основные команды
- `/start` — старт и меню
- `/find <текст>` — явный текстовый поиск (без аргумента — просит прислать описание следующим сообщением)
- `/users` (owner) — список allowed/pending
- `/allow <user_id>` (owner)
- `/deny <user_id>` (owner)
- `/smtp_test` (owner) — проверка доставки на Kindle (Resend/SMTP)

Режимы отладки (`RAW_MODE`, `FLIBUSTA_DEBUG`, `GEMINI_DEBUG`) — переменные окружения, не команды (см. п.7 выше).
